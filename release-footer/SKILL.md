# 版权与发布信息页脚

实现紧凑、整体水平居中的页脚：`© NovaXNS 2026 / Currently v0.7 / [分支图标] cff8cae`，提交号右上方附绿色 `αlpha` 胶囊。
品牌、年份、版本和阶段标签应按目标项目与用户要求设置；示例版本和 SHA 不能作为真实发布数据。

## 外观

- 品牌使用目标项目的名称，不加 @；模板中的 NovaXNS 仅为样式示例。版权年份使用项目约定的年份，不把 2026 永久写死为通用模板。
- 灰蓝文字 `#68757f`、浅灰背景 `#eef1f3`、细顶边框。桌面与手机均以页脚容器为基准整体水平居中，不能在桌面断点改为左对齐。段落清除默认外边距，使用 `display: flex; flex-wrap: wrap; justify-content: center; align-items: center`；版权、版本及提交组在每行垂直居中，窄屏换行后仍水平居中。
- 版本前缀为 `Currently v`；提交号使用等宽字体，展示至少 7 位的 Git 短 SHA，不显示分支名 main。
- 分支图标 18×18，viewBox 为 `0 0 24 24`，描边为 currentColor、1.5px，圆形端点与连接；保持固定尺寸、不收缩并允许 SVG 溢出。使用模板提供的完整三个节点路径。提交组使用 `inline-flex` 和 `align-items: center`，让图标与提交号的元素中心对齐，不依赖基线偏移微调图标。
- 状态标签使用可配置的上标胶囊，白色粗斜体，位于提交号右上方。Alpha 默认显示绿色 `#198754` 的 `αlpha`（首字母是希腊字母 α）；其他阶段按下方对照表设置内容和颜色。标签字号为正文的 75%，内边距 `.35em .65em`，圆角 `50rem`。只对上标应用 `translateY(-.45em)`，不移动正文或图标，也不让上标位移改变正文行的居中位置。图标、提交号与标签作为一个整体换行。
- 页脚置于文档流底部；页面较短时通过主容器 min-height 和内容 flex-grow 推到底部，不覆盖内容。

读取 [assets/footer.html](assets/footer.html) 获取可适配到 React、Vue 或普通 HTML 的外观模板。延续目标项目技术栈，不为页脚引入 UI 框架。

## 发布阶段徽标

默认发布阶段顺序：`Dev → Pre-alpha → αlpha → Beta → RC → Stable`。阶段来自项目发布配置，不把模板示例的 alpha 写死到目标项目。

| 配置值 | 默认内容 | 阶段或维护状态 | 背景色 |
| --- | --- | --- | --- |
| `dev` | `Dev` | 开发中 | `#6c757d` |
| `pre-alpha` | `Pre-alpha` | 早期原型，核心功能尚不完整 | `#6c757d` |
| `alpha` | `αlpha` | 内测版，初步可用 | `#198754` |
| `beta` | `Beta` | 公测版，功能基本完整 | `#0d6efd` |
| `rc` | `RC` / `RC.1` | 发布候选版，进行最终验证 | `#b45309` |
| `stable` | `Stable` | 正式稳定版 | `#198754` |
| `lts` | `LTS` | 长期支持 | `#0f766e` |
| `deprecated` | `Deprecated` | 已弃用，建议迁移 | `#b45309` |
| `eol` | `EOL` | 已停止维护 | `#6c757d` |

LTS、Deprecated 和 EOL 是维护状态，不是 alpha 到 stable 的顺序阶段，只在项目明确配置时显示。允许自定义文字及配色；使用通用 `release-footer__badge` 类并同步设置 `data-stage` 与文字，避免所有内容都沿用 alpha 的类名和语义。橙色和青色使用较深色值以保证白色小字可读。

读取 [references/release-stages.md](references/release-stages.md) 实现配置优先级、版本后缀推断及隐藏正式版徽标。正式版本默认显示 `Stable`，也可按项目配置隐藏；隐藏时移除整个上标节点，避免残留间距。

## 版本信息与发布流程

版本号表示发布版本（如 1.2.3）；提交号标识源码提交。push 不改变 SHA，新的 commit 才改变 SHA。

不可把某个提交的 SHA 写回该提交的源码：这会改变提交内容，再次产生不同 SHA。遵守以下顺序：

1. 检查项目发布方式、工作区、版本来源及现有脚本。完成源码与版本号修改并验证。
2. 在已获提交授权时创建发布提交。不要把使用本 skill 理解成发布或推送授权。
3. 在提交后、推送前读取最终 HEAD：保存完整 SHA，并用 `git rev-parse --short=7 HEAD` 得到显示值。
4. 从该完整 SHA 导出源码到临时目录，把生成的 `release.json` 注入发布目录。该文件不参与 Git 提交，加入项目的忽略规则。不要为更新页脚再创建一次提交。
5. 验证元数据进入生产构建及最终 Docker 镜像。打包并生成 SHA-256 校验文件；按既有工作流推送同一个提交。
6. 核对发布包 SHA、构建内元数据与推送的提交对应关系。不覆盖已交付的同版本包；需要新修复时递增版本。

仅请求页脚实现时，完成代码与验证即可；打包、推送和部署按用户当前授权执行。

读取 [references/release-metadata.md](references/release-metadata.md) 实现元数据加载、缓存处理和发布检查。复用并改进目标项目已有发布脚本，不直接复制某个项目的目录假设。

## 验证与交付

检查桌面与窄屏的整体水平居中、同行正文和图标的元素中心对齐、窄屏换行、SVG 完整性与徽标上标位置。更换为 Pre-alpha、RC.1、Deprecated 等较长内容及隐藏徽标时仍应保持对齐；检查配置优先级和版本后缀推断，没有真实 iPhone 测试时不要声称已在 iPhone 验证。
执行与修改相关的构建和检查。发布时检查压缩包内 release.json、构建后静态文件和最终提交一致，且生成文件没有使 Git 工作区变脏。
说明实现情况与实际验证范围。仅生成包或推送源码时，不宣称远程服务器已经部署。
